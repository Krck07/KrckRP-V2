The Universal Session Format
Do not use these prompts on their own. For every single session, you must combine the session-specific prompt below with this Standard Preamble and Handoff.

Standard Preamble (prepend to every prompt):

System Context: You are an expert Python developer building a local AI RPG engine called KrckRP. We are working in a highly modular, step-by-step fashion.
Knowledge Base: Review the attached KrckRP.md (specifically sections 0, 3, 5, 6, and the section relevant to this task). Review the attached INTERFACES.md to see the file tree, exact file paths, and function signatures generated by previous sessions. Do not invent new paths for existing modules.
Coding Standard: Write complete, functioning files. Include pytest tests in a tests/ directory for the module you are building. Do not use placeholder code unless explicitly asked to create a stub.

Standard Handoff (append to every prompt):

Handoff: At the end of your response, output a markdown block titled ### INTERFACE UPDATE. In it, list the exact file paths you created/modified, all public class/function signatures, and any core assumptions you made. I will copy this into INTERFACES.md for the next session.

The Session Prompts
Session 0: Foundation, Rules, & Contracts
Context: Before writing application code, we must establish the hard design decisions, API contracts, and rules engine blueprint so all future sessions align.
Task: Create the foundation documents and project layout.
Requirements:

Define the project folder structure (e.g., app/models/, app/engine/, app/llm/, app/memory/, tests/).

Make the open decisions: We will use sqlite-vec for the vector store (to keep everything in one DB ecosystem), Server-Sent Events (SSE) for the UI streaming, and a strictly deterministic (no randomness) resolution engine.

Create RULES.md: Define the exact default stat set, numeric scales, formula for resolution, outcome tier thresholds, and capability modifiers.

Create the API contract mapping for the frontend/backend endpoints.

Create a brief KOBOLD_CHEAT_SHEET.md documenting the KoboldCpp streaming endpoint and grammar (GBNF) submission format.
Output: The markdown files above and a shell script or list to scaffold the directory structure.

Session 1: Universal Database Schema & Mock Fixtures
Context: We are building the strict SQLite database schema and a Mock LLM to test the engine without GPUs.
Task: Create the SQLAlchemy/SQLModel models and the mock LLM client.
Requirements:

Create tables for World, Campaign (save slots), Session (play-session records), Character, Location, Item, Faction, Relationship, Ability, Quest, and Summary. Items and Relationships must be their own tables with foreign keys, not JSON blobs.

Add a world_clock field to Campaign.

Create the generic Event log table: id, turn_id, entity_type, entity_id, field, operation (create/update/delete), before_value, after_value, sequence_num, and witness_metadata (who was present/told).

Create mock_llm.py: A client that returns canned narration strings and static JSON extraction dictionaries for testing.

Create a tiny sample "tavern" world fixture to populate the DB for tests.

Session 2: FastAPI Backbone & LLM Routing
Context: The API backend routing requests to KoboldCpp (or the Mock LLM).
Task: Build the FastAPI app skeleton and KoboldCpp connectors.
Requirements:

Create a FastAPI app with endpoints for POST /turn and the SSE streaming route.

Write the HTTP client wrapper for KoboldCpp that supports both Narrator (streaming text) and Extractor (synchronous JSON grammar).

Implement fallback logic for when KoboldCpp is down or timing out.

Crucial: The /turn endpoint must only commit state changes to the database after the narrator stream ends and the extraction succeeds.

Session 3: Frontend UI Skeleton
Context: The local web UI served by FastAPI.
Task: Build the vanilla HTML/JS/CSS frontend.
Requirements:

Implement a campaign/save-slot selection screen.

Create the main play UI: Chat pane (listening to SSE) and text input.

Create the persistent sidebar.

Add the GET /campaign/{id}/state endpoint to the FastAPI app to populate the sidebar (stats, inventory, location, nearby characters, active quests).

Session 4: Turn Pipeline & Extraction Interfaces
Context: The central engine loop that orchestrates the turn and translates text to structured data.
Task: Implement the Turn Pipeline orchestrator.
Requirements:

Define stub interfaces for resolve_action() (returning an Outcome) and assemble_context() (returning a prompt) to be filled in later sessions.

Write the pipeline: Interpret Intent -> (Stub) Resolve Mechanics -> (Stub) Assemble Context -> Narrate -> Extract.

Build the Extractor payload logic: It must receive a list of known entity IDs and names in the current scene to prevent entity resolution failures.

Write a utility to convert the Extractor's Pydantic/JSON schema into GBNF grammar for KoboldCpp.

Session 5: State Mutator, Validation, & Time Travel
Context: Validating LLM outputs and managing strict state via the Event Log.
Task: Implement validation, DB commits, and the undo/rewind engine.
Requirements:

Write the validation service: checks Extractor JSON against DB reality.

Implement commit_turn(): writes valid changes to DB and the Event table.

Implement rewind(): deletes events from a turn onward, using before_value to restore the exact DB state.

Implement "Regenerate" (undo last AI message) and "Edit past message" (undo to turn + replay with new input).

Tests: Write a pytest that takes a DB snapshot, applies 5 mock turns, calls rewind, and asserts the DB perfectly matches the snapshot.

Session 6a: Vector Store & Rollback Support
Context: Episodic memory storage using sqlite-vec.
Task: Implement the semantic memory layer.
Requirements:

Initialize sqlite-vec tables linked to the main database.

Write functions to embed text and store it with metadata (turn_id, session_id, characters present).

Implement rollback hooks so when Session 5's rewind() is called, the associated vector entries are also deleted.

Session 6b: Rolling Summarizer
Context: Compressing history to save context tokens.
Task: Implement the Summarizer module.
Requirements:

Write a background/end-of-turn process that chunks older raw turns into a compressed narrative summary.

Write this summary to the Summary table, linked to turn_id so it can be rolled back during a rewind.

Session 6c: Context Assembler
Context: Building the Narrator's prompt using strict budgets.
Task: Implement assemble_context().
Requirements:

Combine SQL state, active quests, rolling summaries, recent raw turns, and retrieved vector memories into a single prompt string.

Implement a strict token budget per section.

Implement the NPC Knowledge Filter: Ensure NPCs only "know" retrieved memories if their witness_metadata matches.

Session 7: Mechanics & Resolution Engine
Context: Replacing the S4 stubs with the actual deterministic rules engine.
Task: Implement the Rules Engine based on RULES.md.
Requirements:

Write the resolve_action() function.

Evaluate the player's action against difficulty, character stats, and context modifiers (terrain, inventory, relationships).

Output a deterministic outcome tier (failure, partial success, etc.) and pass it as a strict fact into the Context Assembler so the Narrator must respect it.

Session 8: Quest Engine & Debug Panel
Context: Handling emergent quests and building a developer lifeline.
Task: Implement quest lifecycles and the UI Debug Panel.
Requirements:

Write the Quest lifecycle manager: listen to validated Extractor events to transition quests (proposed -> active -> completed/failed).

Build a hidden "Debug Panel" in the frontend and a corresponding API route. It must display: The fully assembled prompt sent to the Narrator, the raw JSON returned by the Extractor, and any proposals rejected by the validator.

Session 9a: World Builder Chat & Schema
Context: Players create worlds by chatting with an AI.
Task: Build the World Generation pipeline.
Requirements:

Create a distinct chat endpoint for world creation.

Use the Extractor pattern to force the AI to output a structured World JSON (locations, factions, tone, ability skins) based on the chat.

Session 9b: Campaign Initialization & UI Editors
Context: Refining the world and starting the game.
Task: Build the Form Editor, Character Creator, and Campaign Initializer.
Requirements:

Build the structured Form Editor UI to manually edit the World JSON.

Build the Character Creation flow.

Write the Campaign Initializer: a function that takes a World template and character data, and instantiates all the necessary rows in Location, Faction, Character, etc., to begin Turn 1.

Session 10: Correction Assistant & Play Sessions
Context: Handling engine mistakes via plain-language and handling long-term play sessions.
Task: Implement the Correction Assistant and Session management.
Requirements:

Create the Assistant API: Provide it a whitelist of strict tools (move_character, set_stat, give_item, update_quest). It cannot write raw SQL.

Implement the Manual Data Editor UI (direct DB form editing).

Implement Play Session logging (start/end session flags).

Tests: Write a "Long-Session Test" using the Mock LLM simulating 50+ turns across multiple sessions to prove the NPC recall, summaries, and context assembler don't crash or overflow.
